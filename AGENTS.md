# grafana-telegram-relay

Правила читаемости относятся ко всем языкам и конфигам. Python 3.15; настройки Ruff и mypy находятся в `pyproject.toml`.

## Актуальность инструкций

- Описывай только целевое состояние и постоянные правила, без временных решений, планов и истории изменений.
- После изменений актуализируй `AGENTS.md`: удаляй устаревшее и сохраняй краткость.
- Версию релиза в формате `MAJOR.MINOR.PATCH` храни в `pyproject.toml`;
  синхронизируй lock и версию в OCI-метаданных Dockerfile.
  Публикация через `make publish` создаёт только тег версии проекта и `latest`, с той же версией в OCI-метаданных.

## Оформление

- Лимит строки — 120 символов; для Python используй `ruff format`.
- Отделяй завершённые блоки и логические части одной пустой строкой во всех языках и конфигах.
- В YAML располагай поля по смыслу: идентификация, основные параметры, затем вложенные структуры. Связанный объект
  оформляй компактно; пустой строкой отделяй самостоятельные логические части и объекты списка. Не сортируй ключи по
  алфавиту.
- Соседние вложенные блоки YAML одного уровня отделяй пустой строкой, даже внутри одного объекта списка.
- Маркеры YAML `---` и `...` используй только по требованию формата или в документах с большим комментарием и схемой
  в заголовке.
- В Python разделяй пустой строкой ветки `elif`/`else`/`except`/`finally` и отдельные шаги логики внутри функции.
- Короткие докстринги — `"""Описание в одну строку."""`. У многострочных открывающие и закрывающие `"""` стоят отдельно,
  текст начинается со следующей строки.
- После любого докстринга оставляй пустую строку перед кодом.
- Описывай назначение каждого модуля в модульном докстринге. У функций, классов и тестов тоже должны быть докстринги;
  секции `Args`, `Returns`, `Raises` — Google-style.
- Комментарии объясняют причину решения и остаются короткими.

## Compose

- Корневые секции: `name`, `include`, `services`, `secrets`, `configs`, `volumes`, `networks`.
- Внутри сервиса соблюдай порядок групп; отсутствующие поля пропускай:
  1. Источник: `container_name`, `image`, `build`.
  2. Запуск: `restart`, `profiles`; затем `stop_grace_period`, `entrypoint`, `command`.
  3. Зависимости и готовность: `depends_on`, `healthcheck`.
  4. Окружение и данные: `environment`, `secrets`, `configs`, `volumes`.
  5. Сеть: `networks`, `expose`, `ports`.
  6. Метаданные: `labels`.
- Отделяй группы и соседние вложенные блоки пустыми строками; связанные скалярные поля оставляй вместе.
- Применяй правила YAML и к содержимому `configs.content`; порты задавай непосредственно в Compose.

## Dockerfile

- Разделяй директивы одной пустой строкой. На строках продолжения `&&` начинается
  со второй колонки, команды — с пятой, как после `RUN `.
- Для команд uv используй BuildKit cache mount; готовый venv копируй в runtime без uv.

## Типы и структура

- Типизируй параметры и возвращаемые значения всех функций, включая тесты.
- Используй встроенные коллекции, `|`, алиасы `type`, `TypedDict`, `Literal` и `Protocol` по назначению. Переопределения
  помечай `@override`.
- Для импортов, нужных только аннотациям, используй `lazy from` Python 3.15.
- Принимай недоверенные данные как `object`, проверяй их на границе приложения и передавай дальше конкретные типы.
- Не обходи проверку через `Any`, необоснованный `cast` или широкие подавления. Точечный `noqa`/`type: ignore[код]`
  допустим с объяснением необходимости.
- Разделяй функции по ответственности; отделяй валидацию от обработки её ошибок. Булевы переключатели делай
  keyword-only, для UTC используй `datetime.UTC`.
- Для типовых форматов и алгоритмов используй стандартную библиотеку или готовые зависимости вместо самописных аналогов.
- Внешние алерты и webhook валидируй строгими моделями Pydantic; настройки — через `Settings`. Для JSON используй
  Grafana-алиасы полей. Секреты загружай из `*_FILE` и храни в `SecretStr`.
- В тестах используй обычные `assert` и `pytest.raises`; проверки не должны отправлять сообщения в настоящий Telegram.
- Общие тестовые фабрики и заглушки держи в `tests/factories.py` и `tests/fakes.py`; не импортируй их из `test_*.py`.
- Проверяй поведение приложения и его интеграцию с зависимостями; не дублируй тесты форматов, парсеров и механизмов
  библиотек.
- Стандартный шаблон — `default.html.j2`: отделяй summary от description, технические значения оформляй кодом.
  Лейбл `mention` выводи один раз под заголовком вне кода; данные алерта экранируй в HTML-шаблонах.
- При resolved редактируй исходное сообщение и отправляй короткий реплай `🟢 Решено` с тем же `mention`.
  Подтверждённый реплай сохраняй в SQLite; повторные webhook и перезапуски не должны отправлять его снова.
- `REMINDER_INTERVAL=0s` отключает повторы. ACK на исходном сообщении или любой копии подтверждает весь инцидент.
  После ACK или resolved удаляй отслеживаемые копии; исходное сообщение и реплай о восстановлении сохраняй.
  Расписание и retry удаления храни в SQLite; уборка работает и при отключённых повторах, и после очистки истории.
  Копии старше суток удаляй заранее из-за ограничения Telegram в 48 часов.
- Canary включается только через `CANARY_ENABLED=true`; по умолчанию webhook и watchdog выключены, очистка истории
  работает независимо от canary. Обычный пример provisioning Grafana не должен требовать canary.

## Проверка

Из корня проекта:

```bash
make check
make build
```

Для проверок используй локальный uv (`~/.local/bin/uv`). Не ослабляй настройки проверок ради прохождения.

Код — в `src/grafana_telegram_relay`, встроенные шаблоны — внутри пакета. Runtime-образ получает установленный wheel в
venv из сборочного слоя; uv в нём нет.
